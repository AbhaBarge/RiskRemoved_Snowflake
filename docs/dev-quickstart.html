Risk & Compliance Copilot

Developer Quickstart — from zero to demo

The one-sentence pitch: An AML analyst's copilot that goes from suspicious signal all the way to a regulator-ready STR filing — where every number comes from SQL, never from an LLM.

1. The Big Picture (30 seconds)

The whole system is a pipeline with 4 stages. Everything else is plumbing to make these stages work.

flowchart LR
    S["SIGNAL\nRule fires on data"]
    E["EVIDENCE\nImmutable pointers\nto source rows"]
    F["FINDING\nLLM-composed\nnarrative + citations"]
    A["ARTIFACT\nSTR filing XML\nready for sign-off"]
    S --> E --> F --> A
1
Signal
Deterministic SQL rules fire on transaction patterns (structuring, income mismatch, sanctions match). No ML. No LLM.
2
Evidence
Pointers (not copies) to the actual rows — txn IDs, party records, policy clauses. Each carries a Snowflake query_id for reproducibility.
3
Finding
An LLM composes a narrative citing the evidence. Versioned, never updated. Every claim must resolve to an evidence row.
4
Artifact
The FIU-IND STR XML file. All numbers from SQL. A human Principal Officer must sign off — auto-filing is legally wrong.
The Golden Rule

No number in a regulatory filing is ever produced by a language model. Every figure comes from a SQL query. The LLM only selects, sequences, and narrates.

Single Agent, Four Modes

One Cortex Agent handles all four roles via system prompt mode-switching. No multi-agent orchestration needed.

flowchart LR
    AGENT["Single Cortex Agent"]
    SE["MODE: SENTINEL\nTriage + prioritize"]
    IN["MODE: INVESTIGATOR\nGather evidence"]
    DR["MODE: DRAFTER\nCompose finding\n+ STR XML"]
    RE["MODE: REVIEWER\nAdversarial check\nevery claim"]
    AGENT --> SE --> IN --> DR --> RE
    RE -->|"REJECT"| DR
    RE -->|"APPROVE"| HU["Human\nPrincipal Officer\nsigns off"]
Sentinel Mode
Reads new signals, opens cases, sets priority. Mostly deterministic — LLM only for ranking summary.
Investigator Mode
Heavy tool use: queries semantic view, searches sanctions, traverses counterparty graph, detects mule rings. Writes EVIDENCE rows. No conclusions.
Drafter Mode
Reads evidence bundle, maps to policy clauses, writes FINDING narrative + STR XML. Every number from SQL.
Reviewer Mode (Critic)
Re-runs stored SQL via Time Travel, compares result hashes, checks citations resolve, verifies clauses in effect. APPROVE or REJECT with specific defects.

3. Where the Data Comes From

Three layers, three technologies. This is important — don't use an LLM to generate transactions.

LayerWhatHowOutput
L1 — Entities Parties, accounts, relationships Python Faker (hi_IN locale) + custom graph builder. Seeded for reproducibility. ~5K parties, ~10K accounts, UBO graph edges
L2 — Transactions The behavioral ledger IBM AMLworld HI-Small dataset, re-skinned to INR/India. Labels are deterministic ground truth. ~5M txns with known laundering patterns
L3 — Narratives KYC notes, case comments, policies AI_COMPLETE via Cortex. Bulk = small model. Golden docs = frontier model. 10K KYC notes, internal AML policy docs
L2 Re-skin Is Non-Trivial

IBM AMLworld is pair-level (sender to receiver). Your schema is leg-level (one row per debit, one per credit). Each AMLworld row becomes two rows. The reskin_transactions.py script must handle: currency conversion (x83 for INR), channel remapping (ACH to NEFT, Wire to RTGS), and this pair-to-leg split.

6. The 5 Detection Rules + 1 Agent Tool

Five signals go into DT_SIGNALS_FAST. MULE_RING_CANDIDATE is a separate stored procedure (recursive CTEs can't incrementally refresh in a DT).

STRUCTURING_CROSS_ACCOUNT
Sub-threshold cash deposits split across multiple accounts of the same party, totaling near or above the Rs 10L CTR trigger. Look for amounts between Rs 9.4L-9.8L per account per month.
INCOME_ACTIVITY_MISMATCH
30-day inflows exceed N times the party's declared annual income (from KYC). A salaried employee declaring Rs 8L/year receiving Rs 50L in a month.
SANCTIONS_MATCH_NEW
A party matches a sanctions entry added since the last check. Exact join of DT_DIM_PARTY against DT_SANCTIONS_CONSOLIDATED on name.
RAPID_CREDIT_VELOCITY
N+ credits from M+ distinct remitters within D days. Classic mule account indicator — money flows in from many sources quickly.
SHARED_DEVICE_CLUSTER
3+ accounts sharing the same device_fingerprint (from ACCOUNT table) with fund flows between them. Synthetic: ~8% of accounts share a fingerprint.
MULE_RING_CANDIDATE (agent tool)
Depth-3 fund-flow cycle via recursive CTE. Not a DT — called on-demand by the Investigator mode via traverse_mule_ring() stored procedure.

10. Pre-Submission Checklist

  • Demo ends at a documented STR filing, not a dashboard
  • Synthetic fraud rate is in the 0.1-1% band (not 10%)
  • No label column in the semantic view (leakage check)
  • All cited regulations are real (not hallucinated circular numbers)
  • System refuses to auto-file (maker-checker enforced)
  • CoCo evidence visible for all 4 lifecycle phases
  • System refuses at least one out-of-scope question
  • Every number in the STR narrative traces to a query result
  • The Reviewer agent catches at least one planted defect
  • Demo works offline (sanctions data pre-loaded, not fetched live)
